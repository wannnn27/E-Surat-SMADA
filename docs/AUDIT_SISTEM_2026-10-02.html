Keputusan audit

Fitur inti sudah relevan untuk pekerjaan TU: membuat surat dari identitas resmi, memberikan nomor, mencatat pembuat, membatalkan dengan alasan, dan membuat rekap. Masalah utamanya adalah konsistensi transaksi, validasi berkas, serta tampilan yang menduplikasi fungsi.

Perubahan telah diterapkan pada kode lokal. Deployment sekolah dan database PostgreSQL produksi belum diubah atau diuji langsung dalam audit ini. Penanganan riwayat Git berisi data, bukti backup/restore produksi, dan pemeriksaan hasil cetak tetap perlu dituntaskan sebelum data nyata dipakai.

Temuan yang ditangani

Prioritas berikut merupakan penilaian dampak pada operasi TU, bukan skor CVSS. Semua baris pada tabel ini sudah ditangani di kode atau lingkungan lokal.

Catatan implementasi dan kompatibilitas

Tidak ada perubahan schema database baru dalam audit ini. Fingerprint permintaan sekarang berawalan v2:; request lama tanpa konteks identitas lengkap tetap berada di riwayat tetapi tidak dapat dirender ulang melalui formulir. Tidak ada nomor lama yang dialokasikan ulang.

Sesi sebelum perubahan versi kredensial perlu login kembali. Perubahan file akun berlaku setelah restart/redeploy semua instance. Penonaktifan template bukan penyimpanan versi historis: upload ulang key yang sama masih dapat memperbarui row sumber.

Validator personel tidak lagi bergantung pada assert yang hilang saat Python berjalan dengan optimasi. Halaman template menjelaskan kontrak field dan perilaku penonaktifan.

Hasil Bandit dibaca dan ditelaah

Pemindaian akhir menghasilkan 46 peringatan, tanpa temuan high severity. Sebanyak 38 adalah B608 pada konstruksi SQL internal. Nama tabel/kolom berasal dari allowlist atau konstanta; nilai pengguna dikirim sebagai parameter. Delapan lainnya terkait subprocess pemeliharaan dengan argumen tetap, password kosong/fixture QA, dan assert pada alat QA. Temuan tersebut tidak disembunyikan dari hasil scanner.

Hasil scanner merupakan petunjuk untuk review, bukan bukti bahwa sistem bebas kerentanan. Pemindaian dependensi langsung maupun lingkungan penuh dilakukan; advisory awal yang berulang tidak dihitung sebagai bug aplikasi terpisah.

Hal yang masih perlu dituntaskan

  1. Riwayat data di Git. Pemeriksaan metadata lokal menemukan 4 commit yang menyentuh folder data. Kandidat commit saat ini bersih, tetapi history/remote dan deployment lama belum dibersihkan atau divalidasi ulang. Audit ini tidak melakukan rewrite history atau mengubah remote.
  2. Deployment PostgreSQL sekolah. SQL penguncian PostgreSQL diperiksa dengan mock; transaksi nyata dan uji bersamaan dijalankan pada SQLite. Pooler, SSL, hak runtime, restart semua instance, dan beban produksi masih perlu diuji langsung.
  3. Arsip file hasil. Riwayat menyimpan register administrasi, belum berkas DOCX/PDF atau snapshot dokumen lengkap untuk unduh ulang. File tetap harus disimpan dalam arsip sekolah. Penonaktifan template tidak menggantikan arsip versi.
  4. Ketepatan tata letak PDF. Konverter memakai interpretasi DOCX sederhana. Font, section, header/footer, pagination, dan format kompleks tidak dijamin identik dengan Word. Petunjuk di layar menyarankan pemeriksaan dan ekspor melalui Word untuk format kompleks.
  5. Operasional LAN dan internet. Aset antarmuka kini lokal. Sinkronisasi offline antara database LAN dan cloud belum tersedia; keduanya harus menggunakan register/nomor yang dikoordinasikan melalui SOP. Jangan menjalankan dua database independen seolah-olah saling tersinkronisasi.
  6. Pembatasan login antar-instance. Limiter sekarang berada dalam memori setiap proses. Untuk beberapa instance publik, gunakan pembatasan di reverse proxy/WAF atau penyimpanan limiter bersama. Tidak ada simulasi DDoS atau pentest eksternal dalam audit ini.
  7. Backup dan akun sekolah. Workflow backup/verify telah diuji sintetis; drill restore produksi dan penyimpanan secret/rilis/template terpisah perlu bukti sekolah. Pengelolaan akun masih memakai file privat dan restart/redeploy.
  8. Uji penerimaan staf. Staf TU perlu memeriksa identitas resmi, standar nomor, contoh cetak, kemudahan kerja, serta SOP pengganti surat. Frekuensi penggunaan fitur belum dikonfirmasi melalui wawancara atau telemetri.

Template hanya boleh berasal dari admin tepercaya. Sandbox render dan batas upload tersedia, tetapi batas CPU/memori/timeout tetap perlu dikonfigurasi pada runtime deployment.

Urutan tindak lanjut

Amankan data historis → rilis ke lingkungan uji sekolah → verifikasi akun dan PostgreSQL → drill backup/restore → pemeriksaan Word/PDF/cetak → uji penerimaan TU → persetujuan penggunaan data nyata.

Audit berdasarkan source, konfigurasi contoh, tes, dokumen operasional, metadata Git lokal, dan browser fixture. Tidak mencetak secret atau identitas master sekolah. Perubahan dari pekerjaan sebelumnya dipertahankan.
